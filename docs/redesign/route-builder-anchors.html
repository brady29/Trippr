The problem today

The plan moves, but the bookings stay put

Trippr works out every date from the trip start plus the nights at each stop. That's great early on, when you can reorder cities and nothing breaks. Once you start booking, it causes trouble. A ticket or a hotel keeps its real date, while the plan around it keeps moving.

The rules package already spots the mismatch (leg-day and stay-dates in checks.ts). But it only tells you afterwards, in the side panel, with no way to fix it.

What happens now

"Can we add a night in Tokyo?"

  1. You press + on Tokyo. It saves straight away.
  2. Hakone, Kyoto, Osaka and Hong Kong all move one day later. The home date moves too.
  3. The Shinkansen and the ryokan you booked for May 15 no longer match the plan. A warning shows up in the Checks panel.
  4. To fix it, you have to work out yourself which stop should give up a night. The only undo is pressing −.
What should happen

The same tap, with the trade-off shown

  1. Trippr knows May 15 is fixed because two bookings depend on it.
  2. It explains that Tokyo and Hakone share 5 nights before that date, and suggests taking the night from Hakone.
  3. Moving the bookings is still possible, but you have to choose it. The bookings affected are then marked needs changing.
  4. A bar sums up what changed, with Undo.
The user journey

Six stages, from "let's go to Asia" to the trip itself

Group trips go through stages, and each stage needs something different from the builder. Early on you need flexibility. Once bookings exist, you need protection. Trippr currently treats every stage the same. The red station is where it hurts most.

The core idea

Bookings turn dates into anchors

An anchor is a date the plan has to keep, because something real depends on it. Anchors split the trip into stretches. Within a stretch the number of nights is fixed, so the stops in it can only trade nights with each other. After the last anchor, nights can grow freely, and only the home date moves.

"Somewhat a constraint" means protected, not frozen. Trippr always looks for a way to keep the booking first. If you really want to move it, you can, but you choose that option on purpose, and the booking is then marked as needing a change.

    How it decides

    The same rule every time. Find the stretch between the anchors around this stop. Offer trades with the other stops in that stretch that aren't locked. Moving a booking is always the last option, shown in red, and it says which bookings it affects.

    Suggested build order

    Three slices, starting with the constraint engine

    Everything else builds on the engine: the fixes for checks, smart add stop, fitting the plan to a booking, and the assistant. So it comes first, in the rules package, with tests, before any screen changes.

    Slice 1 · recommended start

    Anchors, locked stops, Undo

    • rules/anchors.ts: works out the anchors and stretches. planNights and planReorder return the trades and any bookings they'd move. Unit tests in vitest.
    • Real booked dates: stays keep the email's check-in and check-out. Marking a hotel booked asks for its dates.
    • RouteView returns the anchors and each stop's lock state. Checks reuse them.
    • Stop card: locked and between-anchors states, plus the trade panel from the demo.
    • Change bar with Undo for nights, reordering and removing. Drag shows which drop positions are safe.
    Slice 2

    Fixes and booking flow

    • Checks on the stop card with fix buttons from the engine.
    • Fit the plan to this booking in Inbox and when marking something booked.
    • Next to book on the route page, and "Did you book it?" when you come back from a link.
    • The assistant's tools respect anchors.
    Slice 3

    Shaping and pace

    • Smart add stop: position and nights, with the date effect shown first.
    • Pace meter on each stop.
    • Compact view for long routes and phones.
    • Trip setup with a date range and must-dos.
    Open questions

    Three decisions before building

    1. How firm is a booked date?

    Options: a hard block (you have to change the booking first), protected (the default is to keep it, moving it is a deliberate choice), or just a warning (what happens today).

    RecommendProtected. It matches "somewhat a constraint", and plans for groups do change.

    2. Should held tickets and chosen hotels count?

    They signal intent, but nobody has paid yet. Treating them as anchors would make planning early on feel stuck.

    RecommendSoft pins: shown, mentioned in the change bar, never blocking.

    3. Should Trippr know about the flight home?

    Today a route ends at its last stop, and the home date is just the result of the nights. A booked return flight is the biggest anchor there is, but it has nowhere to go yet.

    RecommendAdd an optional "getting home" ticket to the route, so a booked flight fixes the last stretch.
